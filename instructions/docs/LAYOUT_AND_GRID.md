# Layout and Grid: обязательная инструкция

## 1. Назначение

Этот документ задает обязательный порядок работы с сеткой, геометрией и пространством при верстке по визуальным референсам. Применяй его до написания каждого блока и при его приемке.

Сетка определяет структурные отношения, но не заменяет композиционное решение. Цель — получить общие rails, предсказуемое responsive-поведение и достаточное количество воздуха, а не механически заполнить все колонки.

Источники и выходные файлы обрабатывай по `instructions/docs/PROJECT_IO_CONTRACT.md`. Значения ниже — универсальные fallback defaults; подтвержденная project-конфигурация или явное решение пользователя имеет приоритет.

## 2. Базовая модель

Если пользователь или проект не задали другие подтвержденные параметры, используй desktop-модель:

- базовая ширина макета — 1440 CSS px;
- 12 колонок;
- поля слева и справа — 48 px;
- gutter — 24 px;
- максимальная ширина рабочего контейнера — 1344 px;
- базовый структурный инкремент — 8 px.

Размер файла референса не равен CSS-ширине макета. Сначала определи масштаб изображения и нормализуй измерения к базовой CSS-ширине. Например, референс шириной 2880 px может показывать макет 1440 CSS px при DPR 2×.

На viewport шире базового макета контейнер остается ограничен своим `max-width` и центрируется. Он не растягивается вместе с экраном.

## 3. Один источник истины

Единственные runtime-значения сетки объявляются в project-owned
`design_system.layout_source`. По умолчанию это тот же
`src/design-system/styles.css`, что и остальные tokens. Starter уже содержит:

```css
--ds-grid-max-width: 1344px;
--ds-grid-desktop-columns: 12;
--ds-grid-desktop-margin: 48px;
--ds-grid-desktop-gutter: 24px;
/* tablet и mobile заданы тем же pattern */

--ds-grid-columns: var(--ds-grid-desktop-columns);
--ds-grid-margin: var(--ds-grid-desktop-margin);
--ds-grid-gutter: var(--ds-grid-desktop-gutter);
```

Числа калибруются только в этих mode tokens. Breakpoint overrides в том же
`layout_source` переключают лишь три активных aliases; фактические breakpoints
фиксируются в `.site-builder/project.yaml`.

Контентный контейнер, page grid и визуальный grid overlay используют готовые
production exports `Container`, `PageGrid`, `GridOverlay` либо буквально те же
классы `.ds-grid-container` и `.ds-page-grid`. Они читают одинаковые:

- `--ds-grid-max-width`;
- `--ds-grid-margin`;
- `--ds-grid-columns`;
- `--ds-grid-gutter`.

`DS_CONTRACT.foundations.grid` хранит token references, а не вторую числовую
таблицу. `/_design-system` разрешает эти tokens через computed styles. Не
дублируй числа или независимую формулу в JS, section CSS либо специально для
overlay. На любом viewport его `x`, ширина и правый край должны совпадать с
фактической page grid. На широком экране overlay обязан останавливаться на
`max-width` вместе с контентом.

Добавь переключаемый overlay до первого production-блока и по умолчанию держи его включенным во время верстки. Overlay не должен влиять на layout или перехватывать pointer events.

## 4. Grid preflight до кода

Перед реализацией каждого блока сначала составь короткую карту layout. Для каждого крупного элемента определи:

- начальную и конечную колонку либо span;
- общий rail с соседними элементами;
- внешний край и внутренний padding;
- способ выравнивания или центрирования;
- намеренно пустые колонки;
- full-bleed или grid-bound роль;
- порядок чтения и перестроение на tablet/mobile.

Пример карты:

| Элемент | Desktop | Намерение | Mobile |
|---|---|---|---|
| Фото | колонки 1–6 | край фото на общем rail | на всю ширину |
| Текст | колонки 8–12 | колонка 7 оставлена для воздуха | под фото |
| Карточки | по 3 колонки | четыре равных элемента | 2×2, затем стек |

Не начинай с произвольных `margin-left`, `translate` или абсолютных координат. Сначала попробуй выразить композицию колонками, spans, gap и системными внутренними отступами.

## 5. Структурные края и внутренний ритм

Проверяй отдельно два уровня:

1. Внешние края карточек, фотографий, текстовых групп и основных компонентов должны попадать в заявленные колонки.
2. Контент внутри них может иметь padding по 8-пиксельной системе и не обязан начинаться на глобальной линии сетки.

Например, карточка может занимать ровно три колонки, а число и подпись внутри нее начинаться через 24 px. Это корректно, если одинаковый padding повторяется у всей группы.

Не подгоняй очертания букв под линии колонок. Для текста проверяются границы его box, ширина строки, переносы и роль. Оптический край glyph не является структурным rail.

## 6. Воздух и spacing

После распределения по колонкам сравни с референсом не только края, но и количество свободного пространства.

- Не ставь два смысловых элемента вплотную только потому, что они помещаются в соседние колонки.
- Если фото и текст выглядят прижатыми, оставь пустую колонку, увеличь системный gap или сузь один из spans.
- Лучше сохранить дополнительный воздух, чем формально занять всю доступную ширину.
- Различай section spacing, расстояние между группами и внутренний padding. Внешний уровень обычно больше внутреннего.
- Вертикально проверяй расстояния: граница секции → eyebrow → заголовок → описание → контент → следующая секция.
- Горизонтально проверяй не только начало элементов, но и расстояние между их видимыми массами.

Используй обязательную семиступенчатую spacing-шкалу `XS / S / M / L / XL / 2XL / 3XL`: по умолчанию это `8 / 16 / 24 / 32 / 48 / 96 / 128 px`. Она задает внешние и внутренние отступы, gap и вертикальный ритм; используй готовые 2XL/3XL для крупных section gaps, а составные кратные — только когда референс доказывает другое устойчивое значение.

В authored production source каждое структурное `padding*`, `margin*`, `gap`, `row-gap` и `column-gap` должно ссылаться на диапазон `--ds-space-xs` … `--ds-space-3xl` напрямую либо через `calc()`/`clamp()` из этих tokens. Не переписывай совпадающее значение как `padding: 24px`: используй `padding: var(--ds-space-m)`. Нулевые resets и `auto` остаются без token. Оптическое исключение 1–4 px допустимо только с коротким комментарием о причине; уникальный отрицательный offset/overlap из референса остается section-local и записывается в decisions. Повторяющееся исключение сначала рассматривай как кандидата на semantic alias, но не создавай новый шаг шкалы автоматически.

Spacing scale не управляет движением. `transform`/`translate`, reveal distance, navigation scroll thresholds и parallax speed/amplitude используют независимые `--motion-*` либо runtime parameters принятого motion-contract и исключены из spacing consumption/source audit. Совпадение, например, `24px` с `--ds-space-m` не создает semantic alias между layout и motion.

## 7. Full-bleed и вложенные сетки

Фон, декоративная поверхность или медиа могут выходить за основной контейнер либо иметь небольшой inset от viewport. При этом значимый контент внутри них должен продолжать использовать глобальную page grid.

Не вычисляй вложенную grid через проценты от уже уменьшенного full-bleed-контейнера: так поля применятся второй раз, и внутренний контент съедет относительно страницы. Привязывай внутреннюю сетку к viewport и тем же production-переменным, что использует основной контейнер.

Проверяй отдельно:

- внешний край full-bleed-поверхности;
- внутренний page-grid;
- край фотографии;
- край текста и кнопок.

Декоративные круги, маски, фоновые сцены и намеренно обрезанные объекты могут не попадать в колонки. Такое отклонение должно быть композиционным решением, а не случайным offset.

## 8. Центрирование и повторяющиеся группы

- Центрируй элемент относительно фактического box или занимаемого span, а не на глаз.
- Для иконок используй стандартный контейнер, например 48×48 px, и центрируй glyph внутри него.
- У повторяющихся карточек проверяй общие внешние края, центры, верхние линии, padding и текстовые уровни.
- Оптическая коррекция на 1–4 px допустима после геометрического центрирования, если форма glyph действительно выглядит несбалансированной.
- Нечетную группу, которая не помещается равномерно, раскладывай явно. Например, пять групп могут переходить в композицию 3+2, а не переноситься браузером случайно.

### Функциональные якоря и независимые группы

Page grid задает safe rails и крупную структуру, но не является обязательной точкой выравнивания для каждой функциональной группы. Перед позиционированием отдельно определи:

- структурную зону, внутри которой живет группа;
- ее собственный якорь;
- связь с соседними элементами;
- правило перестроения на меньшей ширине.

Возможные якоря:

- левый или правый rail контейнера;
- центр viewport или секции;
- центр отдельной зоны;
- центр свободного пространства между соседними группами;
- край, центр или baseline связанного компонента.

Например, в header логотип и CTA могут попадать в общие rails, а навигация — независимо центрироваться относительно viewport, header или свободной области. Не сдвигай визуально центральное меню на ближайшую колонку только ради совпадения с overlay.

В footer разные группы также не обязаны начинаться на одних колонках. Социальные иконки могут быть самостоятельной центральной группой, тогда как copyright и декоративный глобус образуют правую композицию, привязанную к правому краю или друг к другу. Не разрушай эту связь, распределяя каждый элемент по ближайшей колонке отдельно.

Зафиксируй якорь каждой независимой группы в grid preflight. Проверяй ее по соответствующему признаку:

- edge-aligned — совпадение заявленного края;
- centered — совпадение центров;
- relational — расстояние, baseline и визуальная связь с опорным элементом.

Выбирай структуру, которая выражает намерение: независимое центрирование, трехзонная композиция, распределение внутри области или единая связанная группа. На промежуточных ширинах якорь может измениться: перестраивай группы до появления тесноты и не исправляй конфликт случайным offset.

## 9. Responsive-модель

До desktop-реализации задай предполагаемую трансформацию:

- desktop — 12 колонок;
- tablet — 8 колонок;
- mobile — 4 колонки.

Это начальная модель, а не требование использовать произвольные стандартные breakpoints. Добавляй breakpoint непосредственно перед тем, как текст, изображения, навигация или карточки становятся тесными, теряют иерархию либо выходят из safe rails.

На каждом режиме:

- сохраняй смысловой порядок чтения;
- перестраивай композицию до чрезмерного сжатия контента;
- оставляй изображения внутри экрана или используй осмысленный crop;
- пересматривай намеренные пустые колонки, а не просто уменьшай desktop;
- проверяй фактические computed columns и ширину компонента: общее правило `.page-grid` не должно случайно перебивать специальный стек компонента;
- не исправляй responsive серией анонимных media-query offsets.

## 10. Обязательная геометрическая проверка

После каждого блока включи overlay и проверь минимум:

- 1440 px — базовый desktop;
- 1920 или 2048 px — поведение `max-width` и центрирование;
- 1180 или 1024 px — узкий desktop;
- 900 и 768 px — промежуточное/tablet-перестроение;
- 640 px — граница широкого mobile;
- 390 и 320 px — mobile.

Проверяй промежуточные ширины непосредственно до и после каждого content-driven breakpoint.

Для критичных элементов измеряй не только скриншот, но и фактическую геометрию DOM:

- `x`;
- ширину;
- правый край;
- центр;
- расстояние до соседнего элемента.

Структурные края, заявленные как общие, должны совпадать с сеткой с точностью до 1 px. Не принимай «почти совпавшие» линии без зафиксированной причины.

## 11. Критерий приемки блока

Блок не считается завершенным, пока одновременно не выполнено следующее:

- overlay и production-контейнер используют одну геометрию;
- mode values объявлены только в `design_system.layout_source`, а contract,
  catalogue и consumers содержат лишь token references;
- computed `columns`, `margin`, `gutter` и `max-width` соответствуют активному
  режиму; container, page grid и overlay совпадают по `x`, ширине и правому краю
  с допуском 1 CSS px;
- крупные элементы соответствуют своей карте колонок;
- full-bleed и внутренний grid проверены отдельно;
- расстояния сохраняют иерархию и не делают композицию тесной;
- повторяющиеся элементы имеют согласованную геометрию;
- responsive-перестроение проверено на целевых и промежуточных ширинах;
- от 320 px нет случайного горизонтального scroll;
- нет clipping, collision, сломанных изображений или незадокументированных offsets.

После изменения общего rail, gutter, контейнера или grid-компонента повторно проверь все ранее готовые блоки. Исправляй общую причину в production-переменной или компоненте прежде, чем добавлять локальное исключение.
