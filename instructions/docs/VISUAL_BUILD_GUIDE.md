# Универсальная инструкция по верстке из визуальных референсов

## 1. Цель

Воспроизводи референсы как настоящий адаптивный интерфейс, а не как плоскую картинку. Цель — композиционная и иерархическая эквивалентность, а не буквальная pixel identity. Результат должен использовать общую сетку и небольшой набор токенов, нормально работать на мобильных устройствах и оставаться удобным для дальнейших правок.

## 2. Источники истины

Общий приоритет:

1. последнее явное решение пользователя или утвержденный QA-результат;
2. подтвержденная project-specific конфигурация и канонические материалы;
3. композиционные отношения из референсов для уникальной section-level геометрии, media и декора;
4. production-дизайн-система для подтвержденных общих ролей и controls;
5. единичные размеры и случайные различия на сгенерированном скриншоте;
6. обратимые допущения агента.

Применяй источник истины по домену:

| Что решается | Основной источник |
|---|---|
| Copy, порядок контента и видимая иерархия | явное решение пользователя, затем референсы |
| Логотипы, иконки, предоставленные фото и authored-графика | канонические файлы из `input/` |
| Grid, rails и responsive targets | подтвержденная project-конфигурация и layout-система |
| Повторяющаяся типографика, кнопки, поля, ссылки, icon buttons, content colors и states | production-дизайн-система |
| Доминанта, оси, воздух, crop, overlap и слои блока | референс |
| Уникальные cards/panels, CTA-композиции, media frames, surfaces, radii и декор | референс, пока не доказано cross-section повторение |
| Motion | явное решение или motion-reference, затем универсальный default |

Случайное отличие системного heading или button на одном сгенерированном скриншоте не переопределяет утвержденную production-роль. При этом общий component не должен переоформлять уникальную секцию: ее силуэт, media placement, crop, surface и decor остаются reference-driven. Новый token или variant создавай только при другой семантической иерархии либо повторяющемся доказательстве в разных секциях или экранах.

## 3. Старт проекта

До верстки:

- прочитай все инструкции проекта и примени релевантные возможности Codex;
- полностью прочитай `instructions/docs/PROJECT_IO_CONTRACT.md` и считай `instructions/` вместе с `input/` read-only;
- изучи структуру репозитория, стек, маршруты, команды, стили, компоненты и ассеты;
- рекурсивно проинвентаризируй весь `input/`, затем просмотри полный набор референсов, включая соседние блоки;
- определи их порядок, предполагаемую ширину макета, повторяющиеся rails, типографику, цвета, кнопки, карточки и обработку медиа;
- отличай размеры файла от CSS-размеров: разный pixel width исходников не означает разную ширину макета;
- по умолчанию считай основной desktop-макет рассчитанным на 1440 CSS px;
- не требуй специального именования файлов. Если есть числовой префикс, используй его как порядок;
- сохрани обнаруженные и подтвержденные project-specific значения в `.site-builder/project.yaml`; не изменяй универсальный `instructions/site.config.yaml`.

После анализа задай один общий пакет вопросов только по решениям, влияющим на весь проект. Если шрифт или единый набор иконок не найдены локально, спроси их обязательно. Остальные обратимые решения выводи из референсов и отмечай как provisional.

## 4. Сетка, layout и 8-пиксельная система

До первого production-блока полностью прочитай `instructions/docs/LAYOUT_AND_GRID.md`. Этот документ — единственный источник истины для контейнера, колонок, gutters, rails, grid overlay, spacing, full-bleed-композиций и responsive-перестроения.

Сетка — обязательный этап preflight и приемки каждого блока, а не финальная декоративная проверка. Сначала зафиксируй крупную геометрию и количество воздуха, затем переходи к типографике и деталям. Grid values объявляй только в project-owned `design_system.layout_source`; production pages используют starter exports `Container`, `PageGrid` и `GridOverlay`, а `DS_CONTRACT`/catalogue хранят и разрешают token names без второй числовой копии. Не исправляй системную проблему локальными offsets.

## 5. Минимальная дизайн-система

До реализации полностью прочитай `instructions/docs/DESIGN_SYSTEM_SOURCE.md`. Не создавай большую библиотеку заранее: после анализа всех референсов задай один production source с минимальными provisional foundations и уточняй его по мере верстки. Страница `/_design-system` только импортирует и показывает реальные production exports.

### Типографика

- До подбора weight, tracking и переносов перенеси declarations из `instructions/primitives/foundations/font-rendering.css` в ранний global layer production-кода.
- Дождись `document.fonts.ready` и проверь фактически загруженный family/face. Не исправляй разницу браузерного рендеринга с Figma случайным локальным уменьшением `font-weight`.
- Один раз скопируй `instructions/reference/design-system-starter/src/design-system/` в project-owned `src/design-system/` и калибруй роли только в его `styles.css` либо в одном эквивалентном production-модуле того же entrypoint. Отдельный typography-template не создавай.
- До первого блока проанализируй все референсы и назначь текст по повторяющейся визуальной и смысловой роли, а не по названию секции.
- Primary scale фиксирован и одинаково читается в коде и catalogue: `heading-small`, `heading-medium`, `heading-large`; `body-small`, `body-medium`, `body-large`; Button `small`, `medium`, `large`. `label` и `metadata` — auxiliary. Не добавляй четвертый размер без устойчивого доказательства в референсах.
- Для каждой роли централизованно задай family, size, weight, line-height, letter-spacing и responsive behavior. Все consumers используют production token/class/component этой роли.
- Большинство основных заголовков секций используют `heading-medium`, основной текст — `body-medium`. `heading-large` допустим для hero или крупного CTA, `heading-small` — для вложенного заголовка; это контролируемая S/M/L-иерархия, а не section-local значение.
- Не задавай полный типографический стиль через `.section-name h2`, `.section-name p` или inline-style. Селектор секции может управлять цветом, шириной, placement и композицией, но не создавать новую типографическую роль.
- Если текст той же роли переносится иначе, сначала меняй контейнер, span, `max-width` или осмысленный line break. Не создавай новый `font-size` только ради совпадения одной строки.
- По возможности используй размеры шрифта с шагом 4 или 8 px, а line-height — с шагом 8 px.
- Семантические `h1`–`h6` определяются структурой документа и не обязаны совпадать с визуальным размером.
- Сравнивай не только font-size, но и weight, leading, tracking, длину строки и переносы.

#### Связь со страницей дизайн-системы

- Сначала реализуй роли в production-коде, затем импортируй и покажи их на `/_design-system`.
- Production-страницы и route дизайн-системы импортируют один и тот же `typography_source`; значения не копируются между файлами.
- Образец на странице дизайн-системы обязан использовать тот же role class/component и те же variables, что реальный текст сайта.
- Не стилизуй catalogue через отдельные правила вроде `.type-specimens h1 { font-size: ... }`: такая страница декоративна и не доказывает консистентность production.
- Изменение роли делай в одном источнике; после него должны одновременно обновляться все секции и соответствующий образец дизайн-системы.
- Перед приемкой сгруппируй production-тексты по ролям и сравни computed family, size, weight, line-height и letter-spacing на одном breakpoint. Необъяснимый section-local набор значений — дефект.

### Цвет

- Ограничение палитры относится к контентным цветам: тексту, кнопкам, иконкам, границам, состояниям и акцентам внутри UI.
- Для контента начни максимум с трех основных хроматических ролей плюс светлый и темный neutral. Добавляй не более двух дополнительных контентных цветов, только когда референсы доказывают их необходимость.
- Цветные фоны секций не входят в этот лимит. Сохраняй все обоснованные референсами фоновые цвета, но оформляй их отдельными semantic tokens, например `section-blue`, `section-mint`, `section-coral`.
- Если несколько секций используют визуально одинаковый фон, переиспользуй один токен. Не объединяй явно разные фоновые сцены ради формального уменьшения палитры.
- Для приглушенного текста и поверхностей предпочитай opacity основного semantic color отдельному почти одинаковому hex.
- Цвета состояний, текста, границ, поверхностей и фоновых сцен должны иметь семантические имена.

### Компоненты

Разделяй два слоя. Typography и общие controls должны быть системными с первого использования. Section composition и визуальные контейнеры по умолчанию локальны и должны сначала совпасть с референсом.

- Храни tokens, typography и shared component families под одним production design-system entrypoint. Реальные страницы и `/_design-system` импортируют один source.
- До первого блока создай production-файлы, а не только showcase: общий tokens/theme layer, typography roles, component exports и публичный entrypoint текущего стека.
- Перед реализацией блока сравни его кнопки, поля, ссылки и icon controls со всеми уже созданными production-компонентами. Card/Panel сравнивай для возможного promotion, но не нормализуй заранее.
- Сначала переиспользуй существующий компонент.
- Если роль и структура совпадают, но отличается размер, тема или состояние, добавь ограниченный variant.
- Новый shared component создавай только для отдельной повторяемой роли.
- Неочевидное первое использование остается локальной композицией. Выноси его в shared только когда та же семантика, структура и визуальная конструкция повторились в другой секции или на другом экране; несколько экземпляров внутри одного grid/list не считаются таким доказательством.
- Очевидные primitives — `Container`, `PageGrid`, `GridOverlay`, button, field, link, icon button и typography roles — можно сделать общими сразу. Layout primitives уже входят в starter и должны переиспользоваться всеми routes. Media treatment, Card/Panel, CTA-layout, collage, decor, локальные surface и radius к этой категории не относятся.
- Сгенерированные референсы могут содержать случайные различия размеров. Если кнопка выполняет ту же роль и визуально относится к уже существующей семье, используй ее текущий размер и вариант, а не копируй новое случайное значение. Новый размер допустим только при явном отличии иерархии, плотности или назначения; тогда оформи его как системный variant и покажи на странице дизайн-системы.
- То же правило действует для heading, body, link и icon container. Radius и surface систематизируй только внутри уже подтвержденной component family; уникальный reference-driven container может иметь собственную геометрию.
- Input/textarea/select при наличии образуют одну `Field` family с общими label, helper/error и default/focus/error/disabled states; не стилизуй поле заново внутри каждой формы.
- Catalogue-only button, field или link, который не является production export, запрещен. Card/Panel показывай в catalogue только после его promotion в shared family.
- Перед финалом проверь не подписи в catalogue, а реальные consumers: одинаковый button/field/link/icon-button и любой подтвержденный shared variant должны разрешаться в одинаковые computed typography, geometry, color и state styles во всех секциях.
- Эту проверку не выполняй только визуально: запусти production ↔ catalogue audit по `instructions/docs/DESIGN_SYSTEM_AUDIT.md`. `passed: false` означает, что design-system sync не завершен.

## 6. Работа с графикой и фотографиями

Сначала классифицируй каждый визуальный элемент.

Верстай кодом:

- текст;
- кнопки, ссылки, поля и карточки;
- границы, divider, поверхности, тени и градиенты;
- только действительно простую геометрию и декоративные формы через CSS или SVG, если их силуэт можно точно воспроизвести;
- иконки из согласованного единого набора;
- логотип из канонического brand asset.

Не пытайся воспроизводить фотографии людей, предметов или сцен через CSS/SVG. Не используй целый скриншот секции как фон и не вырезай фото из скриншота для финальной реализации.

Если отдельный канонический photo/illustration asset предоставлен в `input/`, переиспользуй его и управляй только layout/crop. Следующий процесс применяется к фотоматериалу, который существует только внутри референса:

1. Определи его роль, CSS-box, aspect ratio, crop, focal point, композицию и необходимость прозрачного фона.
2. Отделяй исходную композицию ассета от финального CSS-crop. Предпочитай сохранить больше полезного изображения и управлять кадрированием в верстке.
3. Перегенерируй отдельный визуально близкий ассет, учитывая реальное место в верстке: позу или предмет, направление взгляда, свет, свободное пространство под текст и будущий crop.
4. Если в референсе человек или объект показан целиком либо не касается края, генерируй его полностью с безопасным запасом вокруг критичных частей. Не допускай случайно обрезанных головы, рук, инструментов, одежды или других значимых деталей. При сомнении делай исходный кадр шире, чтобы он оставался гибким для desktop и mobile.
5. До генерации определи, нужен ли реальный фон или прозрачная вырезка. Если cutout получился с нежелательным фоном либо генерация необратимо обрезала объект не так, как в референсе, не маскируй дефект в CSS — перегенерируй ассет.
6. После определения максимального CSS-размера генерируй итог с 2× pixel dimensions.
7. Для обычного фото используй WebP. Для вырезанного объекта используй WebP с alpha или PNG.
8. Оптимизируй вес, укажи intrinsic dimensions и подходящий `sizes`/responsive image behavior.
9. Проверь края исходного файла и финальный crop отдельно на desktop, tablet и mobile. Если один исходник не работает, подготовь другой crop или отдельную мобильную генерацию.
10. Добавь содержательный `alt`, если изображение несет смысл; декоративному изображению оставь пустой `alt`.

Не генерируй растровые иконки, стрелки, текстовые логотипы или UI. Если иконка отсутствует, используй согласованный icon set либо запроси канонический вектор.

Самостоятельную authored-графику — органические кривые, сложные blob-композиции, коллажи, иллюстрации и фоновые сцены — не заменяй приблизительной перерисовкой через CSS, Canvas или случайный SVG. Предоставленный asset используй напрямую. Если его нет, подготовь отдельный визуально близкий asset по правилам `instructions/docs/ART_DIRECTION_QA.md`.

## 7. Верстка блока

Для каждого блока работай в одном порядке.

### Анализ

- Посмотри текущий, предыдущий и следующий референсы.
- Выполни grid preflight по `instructions/docs/LAYOUT_AND_GRID.md`, затем разложи блок на текстовые роли, компоненты, медиа и декор.
- Для каждого элемента реши: reuse, variant, new shared или local composition.
- Зафиксируй порядок чтения и предполагаемое поведение на мобильном.

### Static desktop

- Создай семантическую HTML-структуру и точный видимый текст из референса либо предоставленного content-файла.
- Сначала добейся утвержденной карты контейнера, колонок, намеренных промежутков, высоты секции и крупных alignments.
- Затем назначь существующие системные типографические роли и components, после чего настрой crop, цветовые роли и декор. Не вводи локальные размеры системного UI ради pixel-подгонки.
- Не используй фиксированные координаты всего макета и не подменяй секцию картинкой.
- Позволяй контенту определять высоту. Fixed height допустим только при доказанной композиционной необходимости.

### Responsive

- Сохраняй иерархию и порядок чтения, а не просто уменьшай desktop.
- Перестраивай колонки в стек до того, как текст и контролы станут тесными.
- Убирай принудительные desktop-переносы строк на малых экранах.
- Используй `max-width`, `minmax()`, `clamp()`, intrinsic sizing и content-driven breakpoints.
- Изображение должно помещаться или осмысленно обрезаться внутри экрана. Нельзя оставлять огромный canvas, который требует горизонтального скролла.
- Декоративные absolute-элементы на mobile нужно уменьшать, кадрировать, перестраивать или скрывать, если они теряют смысл.
- Проверяй не только заданные viewports, но и промежуточные ширины, где композиция может сломаться.
- От 320 px и выше страница не должна иметь случайного горизонтального scroll.

### Синхронизация системы

- Перенеси в tokens/components системные controls и решения, повторившиеся в разных секциях или экранах. Повтор ряда элементов внутри одной секции не требует global promotion.
- Добавь или обнови пример на странице дизайн-системы.
- Если изменен общий токен или компонент, перепроверь все предыдущие места его использования.
- После sync снова сравни секцию с референсом: систематизация не должна изменить ее силуэт, media placement, crop, воздух или декор.

## 8. Страница дизайн-системы

Создай служебный маршрут `/_design-system` или эквивалент проекта. Он должен открываться прямой ссылкой и использовать реальные production exports.

Покажи на странице:

- палитру и opacity-варианты;
- типографические роли с реальным wrapping;
- spacing scale `XS / S / M / L / XL / 2XL / 3XL` (`8 / 16 / 24 / 32 / 48 / 96 / 128 px` по умолчанию), радиусы, border и surfaces;
- все семь spacing steps присутствуют в contract/catalogue, а каждый фактически используемый в production step потребляется через token в `padding`/`margin`/`gap`; declarations с совпадающим raw `px` считаются drift от token source;
- motion transforms, reveal distances и parallax parameters не считаются spacing consumers и проверяются отдельно по motion-contract;
- кнопки и ссылки во всех размерах и состояниях;
- иконки и правила их контейнеров;
- формы и только подтвержденные shared cards/panels, если они есть в проекте;
- все фактически созданные shared components и variants;
- desktop/tablet/mobile контейнеры;
- переключаемый overlay: колонки, gutters, rails и базовые линии с шагом 8 px.

Не копируй markup или CSS компонента в каталог. Исправление production component должно автоматически обновлять каталог и все страницы.

## 9. Motion и интерактивные состояния

До реализации движения полностью прочитай `instructions/docs/MOTION_AND_INTERACTIONS.md`. Он является источником истины для базового появления заголовков и контентных блоков, внутреннего media parallax, а также поведения кнопок, ссылок, навигации, icon controls и кликабельных поверхностей, если пользователь или утвержденный дизайн не задали другой язык движения.

Каждый видимый интерактивный элемент должен реально работать либо иметь явно согласованное временное поведение. Не добавляй `scale`, подъем, смещение или тень как универсальный hover по умолчанию. Геометрия контрола должна оставаться стабильной; состояние выражается внутри компонента через цвет, заливку, underline, label transition или тихую подложку.

Для появления контента используй только три default-семьи из motion-гайда: reveal заголовка, вертикальный slide-reveal абзаца или блока и небольшой параллакс изображения внутри неизменного контейнера. Источник поведения — `instructions/reference/motion-sandbox/`; переноси его механику, не воспроизводи анимации заново по этому абзацу. Не изобретай дополнительные blur-, rotate-, scale-, horizontal-slide- или wipe-анимации без отдельного решения.

## 10. Текст

Воспроизводи читаемый текст со скриншотов дословно, включая регистр и порядок. Не заменяй его случайным lorem ipsum. Если важный текст не читается, задай вопрос в общем onboarding-пакете; если ответ не получен, используй осторожную provisional-транскрипцию и отметь допущение вне пользовательского UI.

## 11. Минимальная проверка

До design-system sync и повторно перед приемкой полностью прочитай `instructions/docs/ART_DIRECTION_QA.md` и выполни отдельную композиционную сверку реализации с референсом. Технически корректная сетка и `design-system-audit.passed: true` не считаются приемкой, если силуэт блока, масштаб медиа, crop или характерная графика визуально не совпадают.

После каждого блока:

- открой его в реальном браузере после загрузки шрифтов и изображений;
- сравни с референсом на основной ширине из project-конфигурации; универсальный fallback — 1440 px;
- проверь 1024, 768, 390 и 320 px, а также ширины непосредственно до и после content-driven breakpoints;
- сначала сравни сетку и геометрию, затем типографику, spacing, crop, поверхности и декор;
- проверь отсутствие горизонтального scroll, clipping, collisions и сломанного crop;
- пройди интерактивные элементы мышью, клавиатурой и focus navigation;
- проверь console errors, failed requests, missing assets и layout shift;
- запусти существующие build, lint и релевантные tests.

После каждых двух блоков проверь собранную страницу целиком: rails, вертикальный ритм, границы секций, повторное использование компонентов и responsive continuity.

## 12. Правки и завершение

Классифицируй каждую правку:

- глобальная сетка, типографика или цвет → token;
- повторяющаяся форма или поведение → shared component/variant;
- responsive-проблема → правило компонента или breakpoint по условию поломки;
- уникальное композиционное исключение → локальное правило с коротким объяснением.

Не исправляй повторяющуюся проблему серией локальных offsets. После системного исправления повтори проверку всех затронутых блоков.

Работа завершена, когда все референсы обработаны, страница дизайн-системы соответствует production UI, адаптивность работает от 320 px, интерактивные состояния и клавиатура проверены, консоль чиста, сборка проходит, а оставшиеся отклонения явно перечислены.
